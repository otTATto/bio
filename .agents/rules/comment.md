# コメントに関するルールや考え方

## 全般

- 自明な処理にコメントしない（コード・型・命名から読み取れることは書かない）
- 既存のコメントを破壊しない
- この変更・この差分に固有の経緯（「従来は」「今回」「〜を外した」等）を書かない（コードの最終的な読み手はその経緯を知らない）
- コメントの量はその影響範囲、つまりどれだけ多くの場所から呼び出されるかに依存する
  - 他の場所から呼び出されうる定数・関数は丁寧に説明する
  - 関数は JSDoc に近い書き方を心がける

## コメントを追加する前に必ず注意するべきこと

コメントを追加するときは、利用者に必要な情報かを以下の 3 点で確認する。

処理への補足コメントは、3 点をすべて満たす場合に書く。公開 API のドキュメントコメントは契約の説明として必要なため、説明を省くのではなく、識別子の言い換えだけにならない内容にする。

1. **言い換えでない**：直下のコード・直上の既存コメントを日本語に翻訳しただけではないか
2. **初見で必要**：この差分・その背景にある会話・関連するレビューなどの文脈を一切知らない人が、3 ヶ月後にこのファイルだけを開いたときに必要な情報か
3. **コードに書けない**：命名・型・構造で表現できない情報か（表現できるなら、コメントを足すのではなくコードを直す）

補足コメントの必要性を吟味し、公開 API には利用者が判断できる契約を残す。

## ではどこに書けばいいのか

情報の内容に応じて、コード・PR・設計文書の適切な場所に記録する。

コードの利用契約に含まれない経緯や設計判断は、以下の場所に記録する。

| 内容 | 行き先 |
| ---- | --- |
| なぜこの変更をしたか・何が問題だったか | PR の本文・コミットメッセージの本文  |
| レビュー指摘への対応内容 | PR のコメント |
| 設計判断・複数ファイルにまたがる背景 | `docs/` 配下のドキュメント |
| どうしてもコードと 0 距離で結びついているべき情報 | これはコメントとして書いてよい |

## コメントの例

### 型定義

```typescript
// src/types/user.ts

/**
 * 商品
 *
 * - id         : 商品の一意識別子
 * - name       : 商品名
 * - price      : 価格
 * - imageUrl   : 商品画像の URL
 * - isAvailable: 購入可能かどうか
 */
export type Product = {
  id: string;
  name: string;
  price: number;
  imageUrl: string;
  isAvailable: boolean;
};
```

### 関数定義

```typescript
/**
 * @function 商品価格の一覧を受け取り、表示用の価格情報に整形して返す
 *
 * @param prices 商品 ID と価格の対応
 * @returns 商品 ID をキーとし、価格と通貨表示を持つ Record
 *
 * NOTE:
 *   - 価格が 0 未満の商品は結果に含めない
 *   - 入力に含まれるすべての商品 ID が返り値に含まれるとは限らない
 *
 * e.g.
 *   - @param prices { 'book-1': 1200, 'book-2': 0 }
 *     ↓
 *     @returns {
 *       'book-1': { amount: 1200, formatted: '¥1,200' }
 *     }
 */
export const formatProductPrices = (
  prices: Record<string, number>,
): Record<string, { amount: number; formatted: string }> => {
  ...
};
```
